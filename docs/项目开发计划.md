# 闲鱼多账号与相关能力 — 原生集成项目开发计划

> **读者**：内部产品 / 工程  
> **范围**：在本珠宝 / 订单管理产品中，以**一等公民模块**（后端 Spring Boot + 现有前端技术栈）实现闲鱼多账号及相关能力；**不**采用嵌入或壳化 `third_party/xianyu-super-butler` 的方式交付。  
> **参考**：仓库根目录 `闲鱼SuperButler说明.md` 仅为**能力调研与边界备忘**（多账号维度、Cookie 等概念启发），**不代表**本产品的集成路径、合规结论或技术选型依据。

---

## 1. 背景与目标

### 1.1 为何选择「原生集成」

- **一致体验**：管理端与售前 / 售中客服在同一套账号体系、权限模型与审计链路内操作，避免维护两套登录、两套数据口径。
- **可控演进**：接口、限流、重试、观测与密钥管理可按企业标准统一实现，便于与订单、客户、库存等业务域做事务级或准事务级联动。
- **降低运维耦合**：不依赖外部 Python 服务常驻、不绑定第三方前端的发布节奏；部署形态与现有 `backend` / `frontend` 对齐。

### 1.2 业务角色与场景

| 角色 | 典型诉求 |
|------|----------|
| **管理员** | 绑定 / 解绑闲鱼账号、分配可见范围、查看健康与审计、配置限流与告警阈值。 |
| **售前 / 售中客服** | 在授权账号下查看会话与消息、回复买家、标记跟进状态；必要时与内部订单 / 客户档案关联。 |

### 1.3 合规与平台风险（简要、中性表述）

闲鱼用户协议与平台规则对自动化、批量操作、非官方客户端等有约束；任何消息同步、自动回复或脚本化行为均存在**政策变更、功能受限或账号处罚**风险。本计划中的工程能力以「在合法合规前提下、由企业自主评估后启用」为前提；**具体是否允许某种交互方式，需以闲鱼现行规则及法务意见为准**，本文档不给出法律结论。

## 2. 能力分层

> 与闲鱼之间的实际数据通道（官方开放能力、网页端行为模拟等）**不在此承诺具体接口形态**；S1「全套」中的模块以行业常见诉求描述，落地时以**官方能力可用性 + 逆向 / 非官方路径的稳定性与合规评估**为准。

### 2.1 MVP（第一阶段）

| 能力域 | 说明 |
|--------|------|
| **多账号绑定** | 支持多个闲鱼账号与内部租户 / 组织绑定；账号级元数据（别名、负责人、启用状态）。 |
| **凭证安全存储** | Cookie / Token 等敏感凭据加密落库；按账号隔离；支持轮换与失效标记。 |
| **会话 / 消息拉取与回复** | 在授权账号维度拉取会话列表与消息；人工发起回复（与客户交流的基础闭环）；失败可重试、可追踪。 |
| **账号状态与健康** | 登录态是否有效、最近同步时间、错误码摘要；便于运营判断是否需重新授权。 |
| **基础审计与权限** | 谁在何时对哪个账号执行了读 / 写；与现有 RBAC 对齐；敏感字段脱敏展示。 |

### 2.2 S1（扩展阶段 — 「全套」能力方向）

在 MVP 之上，按优先级逐步扩展（模块名可按最终实现拆分）：

| 模块方向 | 价值说明 |
|----------|----------|
| **关键词 / 规则与自动回复** | 基于关键词或简单规则辅助首响；需单独评估频率与平台风控。 |
| **订单 / 交易信息同步** | 与内部订单、定制工单对齐；**以官方或稳定数据源为准**，避免硬编码未文档化字段。 |
| **议价 / 价格辅助** | 展示历史议价、内部底价提示（业务规则在己方系统内配置）。 |
| **统计与导出** | 按账号 / 坐席 / 时间维度的会话量、响应时长、转化相关指标；导出权限受控。 |
| **监控与告警** | 同步失败率飙升、大量 401/403、单账号 QPS 触顶等可观测信号对接现有告警渠道。 |

未列入表内的能力（如商品批量上下架、站外引流检测等）可在 S1 后期按产品路线图增列；**凡依赖闲鱼未公开契约的能力，均须标注「依赖稳定性评估」后再排期**。

## 3. 技术架构原则

### 3.1 服务边界

- 建议在后端划分独立聚合或 Maven 模块（命名示例：`xianyu-integration`），对外暴露**应用服务接口**，由现有 `Order` / 用户模块通过接口调用，避免闲鱼相关代码散落在各 Controller。
- 与闲鱼通信的适配层（HTTP 客户端、签名、序列化）与**领域模型**（账号、会话、消息、同步游标）分离，便于替换数据源或降级。

### 3.2 账号维度隔离

- 所有队列任务、缓存键、限流计数器均携带**内部账号 ID**（及租户 ID），禁止跨账号混用连接或凭据。
- 并发策略：单账号内串行或有限并行，避免触发平台侧异常风控（参数可配置）。

### 3.3 凭证加密与密钥管理

- 使用信封加密或 KMS / 主密钥派生；库内仅存密文与密钥版本号。
- 轮换：支持主密钥轮换后分批重加密；旧版本只读解密直至全部迁移。

### 3.4 队列、限流与背压

- 拉消息、发消息走异步队列（如现有消息中间件或 DB 队列表），统一**全局限流 + 每账号限流**。
- 可配置退避与最大重试；死信队列便于人工介入。

### 3.5 可观测性

- 结构化日志（账号 ID 用内部 UUID，闲鱼侧 ID 按需哈希）；指标：成功率、延迟、队列深度；分布式追踪可选。

### 3.6 与现有用户 / 角色体系对齐

- 「能操作哪些闲鱼账号」映射为资源级权限（如 `xianyu:account:{id}:read`），复用现有认证与审计中间件模式。

## 4. 阶段与里程碑

### 4.1 MVP

| 里程碑 | 交付物概要 | 验收标准（示例） | 主要依赖 |
|--------|------------|------------------|----------|
| M0 设计冻结 | 数据模型、API 草案、威胁模型初稿 | 评审通过 | 产品范围签字 |
| M1 账号与凭证 | 绑定流程、加密存储、权限模型 | 测试环境多账号绑定 / 轮换用例通过 | 密钥管理方案 |
| M2 消息闭环 | 拉取 + 人工回复 API 与管理端最小界面 | 指定账号端到端收发成功、审计可查 | 闲鱼通道 PoC 稳定 |
| M3 健康与运维 | 健康检查、基础告警、文档 | 失效凭据可识别、运维可处理 | 监控平台对接 |

### 4.2 S1

| 里程碑 | 交付物概要 | 验收标准（示例） | 主要依赖 |
|--------|------------|------------------|----------|
| S1-a 规则与辅助 | 关键词、模板回复（可关闭） | 规则命中与发送符合配置、全链路审计 | MVP 稳定运行 |
| S1-b 订单对齐 | 与内部订单 / 客户关联设计实现 | 关联数据一致、冲突策略明确 | 订单域 API 稳定 |
| S1-c 统计导出 | 报表与导出 | 权限与脱敏符合安全评审 | 数据仓库或导出管道 |
| S1-d 告警完善 | 多维度告警与 Runbook | 演练通过 | 告警渠道 |

各阶段上线前建议保留**灰度账号**与**功能开关**，便于快速降级。

## 5. 数据与安全

| 主题 | 原则 |
|------|------|
| **Cookie / Token** | 仅服务端解密使用；禁止写入前端 LocalStorage 明文；传输全程 TLS。 |
| **密钥轮换** | 主密钥定期轮换；应用层记录 `key_version`；轮换窗口内兼容解密。 |
| **最小权限** | 坐席默认仅能访问被授权的账号；管理操作与普通会话操作分权。 |
| **日志脱敏** | 消息正文、买家昵称等按策略截断或哈希；调试日志分级开关。 |
| **数据留存** | 与法务一致的消息留存周期；删除 / 导出请求流程预留。 |

## 6. 风险与对策

| 风险 | 对策方向 |
|------|----------|
| **平台接口或页面结构变更** | 适配层隔离、契约测试、版本化配置；关键路径监控与快速回滚。 |
| **封号或限制登录** | 健康检测与用户提示；单账号故障不影响其他账号；Runbook 含重新授权流程。 |
| **消息延迟或丢失** | 游标 / 增量同步设计；幂等发送；对账任务（可选）发现缺口。 |
| **内部滥用或误操作** | 审计 + 审批（如批量操作）；敏感操作二次确认。 |

---

## 7. 开放问题（需产品 / 法务 / 业务确认）

1. 企业是否允许在现行闲鱼规则下开展**自动或半自动**回复、同步频率上限目标值。  
2. 消息与个人信息**留存周期**、跨境 / 个人信息保护法合规要求。  
3. 售前 / 售中与**订单系统**的关联粒度（会话级、商品级、定制工单级）。  
4. 是否必须**仅官方渠道**采集数据；若评估非官方路径，责任边界与退出策略。  
5. 多租户场景下闲鱼账号归属（公司主体 vs 个人代运营）及合同条款。  
6. 与竞品或第三方工具的数据迁移 / 并行期是否允许，以及安全审查要求。
